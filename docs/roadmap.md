## Scoped but deliberately deferred
- Categories + cross-brand substitute-product recommendations (e.g. Tnuva milk 3% suggesting Tara milk 3% as a cheaper/better-rated alternative). Two sub-problems: (1) category data audit needed first — GS1's group_id/group_name only covers ~10% of catalog (GS1-matched items), no category source confirmed for the rest; (2) substitute matching is structurally the same risk class as the already-deferred cross-chain PLU-matching problem in handoff_super.md ("a wrong match is worse than no match") — treat with equal caution, high-confidence-only matching, no best-guess fallback. Sequenced deliberately AFTER ratings & reviews shipped, since "better rating" as a ranking signal has a cold-start problem and needed real rating data to exist first.
- User-facing email for flights (price alerts) — a genuinely different problem from SU10S-7's internal moderation alerts, and the SMTP-through-a-mailbox approach does NOT carry over: mail to strangers' inboxes means deliverability, bounce handling, unsubscribe headers and sender reputation. Evaluate Mailgun or Resend when that lands. **SendGrid is paid-only since 2025** — the free plan it was originally chosen for no longer exists.
- **Sub-chains as separate chains — DECIDED (Dude, Sept 27 2026): separate chains, NOT labels.** They are branded and marketed as separate entities, so a Bnei Brak search should show יש חסד as its own chain rather than as "שופרסל". Today every Shufersal format (יש חסד, יוניברס, דיל, שלי, אקספרס …) collapses into one chain name; Fresh Market has the same pattern across 7 federated brands. **Do this in the same session as the StoresFull address ingestion item below — it touches the same files.** *After the mobile apps launch.*
  - **The scraper does not change.** Price files are published under the PARENT chain code (Shufersal `7290027600007`), so fetching stays exactly as it is. The split is a brand layer *above* it: store → brand → parent chain.
  - **Every user-facing grouping moves from `chain_id` to brand**: chain list and filters, the "מחפש ב-N רשתות" count, `/basket/compare` aggregation *and its winner selection*, `/coverage`, the mobile chain picker, and saved filters. The compare change is the one with teeth — the winner is currently chosen per `chain_id`, so splitting brands changes which chain wins a basket.
  - **Verify the source data, do not assume it.** Three candidate signals exist and none is confirmed: `stores.sub_chain_id`, Shufersal `store_name` prefixes ("יוניברס - …"), and `SubChainName` in the StoresFull XMLs. Establish which is actually populated and consistent before designing on top of it.
  - **BE stores stay excluded.** CLAUDE.md marks this SEVERE — "never merge BE-branded Shufersal stores into the main chain", they are pharmacy/beauty, not groceries. Note the trap this creates for *this* work specifically: a naive "split every sub-chain into its own brand" would surface BE as a grocery chain for the first time. BE must remain out entirely, not become brand number six.
- **Address passthrough from the store files (SU11A-13).** `shufersal.py`, `victory.py`, `hazihinam.py` and `binaprojects.py` drop the `Address` field every chain publishes: **395 of 637** city-precision stores have a numbered feed address we never store (Shufersal 259, Victory 63, King 26, Shefa 22, Shuk HaIr 15, Hazi Hinam 10). Pass it through (no new table — `stores.address` exists; `address_override` keeps hand fixes), then the weekly `geo_nominatim` run places them (~69% hit rate so far → ~270 stores). **Risk: `parse_address`** on feed strings with the city glued on ("תרצה 19ר״ג") or prefixes ("רח' …") — test on a sample first.
- StoresFull XML address ingestion — six chains publish NO address in our data at all (שופרסל 321 stores, ויקטורי, קינג סטור, שפע, שוק העיר, חצי חינם), so just over half the network can only ever be placed at its city centre. Their StoresFull XML may carry addresses our loaders drop. **Read-and-report first** — confirm the field exists before scoping an ingestion change, since this touches the scraper path.
  - Hazi Hinam and Shufersal scrapers don't apply STORE_CITY_OVERRIDES; fix during StoresFull work. (SU10S-25: `hazihinam.py` / `shufersal.py` write the feed city directly, so an override for those chains only takes effect through a `build_city_canonical` rebuild, not the nightly load.)
- 105 serving stores have no `city_canonical` — so they get no coordinate at all, not even a centroid (206 across all physical stores). 91 are Carrefour, 12 Hazi Hinam. Separate from the address problem: these lack a usable CITY, which is a city-matching gap rather than a geocoding one.
- Weighted-item barcode scanning (scale-printed codes) — Israeli in-store scale barcodes (prefix 27 confirmed, likely varies by chain the same way promo encodings do) embed price/weight per-label, so no base product exists to resolve to. Needs backend parsing per chain, mapping to underlying catalog item. Not started, not trivial — treat similarly to the promo unit-mismatch problem (per-chain verification required, no universal format).
- Orphaned GS1 images — 262 JPEGs on disk sit outside the image job's target set, so SU10S-1's deletion fix never visits them and `_image_path()` serves them forever. Reconcilable against `media_assets`, which carries per-GTIN `filename` and `hidden` fields (confirmed present on 100% of sampled products, avg 2.8 assets each) — so a sweep can diff the directory against what GS1 says should exist, without re-fetching. Needs its own small job; not started.
- Search_Words as a search-ranking input — GS1 publishes supplier-authored search terms (74% fill, e.g. a yogurt listing "יוגורט לספורטאים", "עשיר בחלבון", "אחרי אימון"). This is a **ranking** change, not a display one, and ties directly to the existing Hebrew search precision item rather than to the GS1 display work. Unscoped; would need care that supplier-authored keywords cannot be used to spam their way up the results.
- Price history (4th product-detail tab, monthly/yearly price trend) — requested Sept 26 2026. NOT buildable today: the scraper cron overwrites price rows on every run rather than preserving dated records ("Snapshot pricing only" — a standing architectural decision). Requires: (a) new price_history table (preferred over making `prices` itself append-only, which would have much wider blast radius across the read path), (b) accepting there is NO backfill possible — history only accumulates from whenever it's turned on, (c) real storage-growth consideration (prices is already ~3.7GB at snapshot-only, re-measure at build time). Connects to the older, already-listed "Promotions + price history" pending item — same prerequisite, don't duplicate scoping. Decision made this session: do NOT build a placeholder 4th tab ahead of the data existing — an empty tab reads as broken, not as "coming soon."
